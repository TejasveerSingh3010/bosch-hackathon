# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

AI-driven chaos engineering against Online Boutique (Docker Compose, `app/docker-compose.yml`). Windows-first: helper scripts are `.bat` files in `scripts/` that use `.venv\Scripts\python.exe` (created by `scripts\setup.bat`).

## Commands

```powershell
.venv\Scripts\python.exe -m pytest                                  # all tests (no Docker needed)
.venv\Scripts\python.exe -m pytest tests/test_safety.py::test_name  # single test
.venv\Scripts\python.exe -m ruff check .                            # lint (config in pyproject.toml, line length 110)

python -m orchestrator targets | actions | stop | recover
python -m orchestrator run --target adservice --action kill --duration 20 [--dry-run]
python -m orchestrator run --target frontend --action spike --duration 30 --rps 20 --users 5
python -m orchestrator run --target currencyservice --action throttle --cpus 0.05 --duration 30
python -m orchestrator run docs\experiment.example.json            # plan-file form (what the planner will emit)
python -m planner list | health | details <attack>                 # Agent 1: the attack catalogue / cluster health
python -m planner rank [--limit 5]                                  # 5 deadliest non-kill/pause/stop attacks now -> results/attack_ranking.json
python -m planner interpret "REQUEST" --out F; python -m planner execute F --confirm  # the dashboard's attack console
python -m planner run --goal "..." --limit 3 [--approve ID ...] [--auto] [--dry-run]  # plan + run, y/N per injection
python -m mapper                                                    # results/graph.json + docs/dependency_graph.png
python -m remediation propose [RESULT_ID ...] | review ID | verify ID | list | recover   # verify is optional
python -m remediation propose-code DECLINED_ID [--no-build]        # code recommendation for a declined proposal
python -m remediation [-v] eval                                     # re-check every proposal with today's checks (no LLM)
python -m agents run PLAN.json [--dry-run] [--no-code] [--session S]  # graph: attacker -> reporter -> remediation -> escalate
python -m agents graph | langfuse-prices                            # Mermaid of the graph | register model prices in Langfuse
```

Live runs need the app (`scripts\app-up.bat`), the monitor (`scripts\monitor.bat`) and a baseline (`scripts\baseline.bat`). Exit codes from the orchestrator CLI: 0 ok, 1 error, 2 plan rejected, 3 aborted.

## Architecture

The pieces communicate through **files in `results/`**, not imports:

- `monitor/` is a standalone host process (`headless_monitor.py`, plus the Streamlit `dashboard.py`). It writes `telemetry.json` (last 60 samples), `telemetry_log.jsonl` and `SLA_BREACH.flag` every 2 s. Its modules are run as scripts and use flat imports (`import boutique_core as core`), not package imports. Only one process may write telemetry; `monitor.bat` sets `BOUTIQUE_DASHBOARD_WRITES=0` on the dashboard. The dashboard's resilience score (`resilience.py`, pure functions) is a weighted sum of five measured factors (availability from the telemetry log; fault tolerance, recovery, failure handling and detection time from the newest result per service+action in `results/`); a factor with no data drops out and its weight is redistributed.
- `safety/telemetry.py` (`TelemetryReader`) is the orchestrator's only view of system health: it reads those files and treats stale data (>15 s) as unsafe.
- `results/STOP` is the kill switch, and `results/active_experiment.json` is the crash-recovery journal (written before injection, cleared after rollback; a present journal blocks new runs until `recover`).

Experiment flow (`orchestrator/runner.py`, `ExperimentRunner.run`):
`schemas.Experiment` → `safety.validate_plan` (allow-list from `target.yaml`, protected containers, single-container resolution, duration cap with a hard 600 s ceiling, thresholds may only be tightened, pre-flight health/freshness) → `ValidatedPlan` → journal → `injector` action `apply` → `Watchdog` polling (aborts on two consecutive breaching samples; stale telemetry aborts immediately) → `rollback` in a `finally` → wait for recovery → `schemas.ExperimentResult` written to `results/<id>.json`.

- `injector/actions.py`: `FailureAction` subclasses (`kill`, `stop`, `pause`, `spike`, `throttle`, `memory_limit`, `network_partition`, `network_delay`, `flapping`) registered in `ACTIONS`/`build_action`. The last four are the day-2 additions: `memory_limit` caps memory in place like `throttle` does CPU (same restore-or-host-total rollback, re-inspected); `network_partition` disconnects the container from its Compose network and reconnects it with its journaled aliases; `network_delay` adds `tc netem` latency/loss via a throwaway `nicolaka/netshoot` sidecar (`Docker.tc`) and deletes the qdisc on rollback (deleting one already gone is success); `flapping` pauses/unpauses on a background thread until rollback. `docker_cli.py` gained `update_memory`/`host_memory`, `network_connect`/`network_disconnect`, `tc`, and `Container.mem_limit`/`networks`; `tests/fake_docker.py` models all of them. Rollback must be idempotent: it inspects the container and does only what is needed, since `restart: unless-stopped` may already have restarted a killed container. `spike` targets `BOUTIQUE_URL`/`target.yaml` `frontend_url`, never a host from the plan. `throttle` (`docker update --cpus`) restores the limit in its journaled pre-state (`recover` passes it back via `FailureAction.resume`); Docker ignores `--cpus 0`, so "unlimited" is restored as the host CPU count, and rollback re-inspects and raises if the limit did not change.
- `injector/docker_cli.py`: `Docker` is a Protocol; `DockerCli` shells out to the `docker` binary with fixed argument lists. Tests substitute `tests/fake_docker.py` (`FakeDocker`), which models restart policies, pause, restart counts and injectable failures (`fail_on`).
- `mapper/`: builds the dependency graph from the Compose file's `*_ADDR` env vars, cross-checks against the upstream architecture, and scores criticality as a weighted sum (explainable, not learned). `frontend` scores low on purpose (internal blast radius).
- `remediation/` (phase 5): the agent only **recommends**; accepting or rejecting a recommendation (`review`) is the human escalation step, and a proposal left "awaiting review" is the normal end of the agent's work. `agent.py` asks an LLM (Groq, `openai/gpt-oss-120b`, key `LLM_API_KEY` in `.env`) for a `ProposalDraft`; `policy.py` checks it deterministically (allowed Compose settings, protected `redis-cart`/`loadgenerator`, every evidence value looked up in `results/<id>.json`, env vars only from `docs/services.yaml` `tunable_env`); `store.py` records the human's decision tied to SHA-256 hashes of `proposal.json` and `override.yml`; `verify.py` (optional, for a human who wants to measure an accepted fix) runs the same experiment N times on the original config and N times with the fix (applied as a Compose override, always restored in a `finally`) and returns effective / ineffective / inconclusive / regressed. Everything lands in `results/remediation/`. Groq's free tier allows 8,000 tokens/minute, so the agent context in `build_context` is deliberately compact. Both contexts include Agent 2's report on each record when `reports/<id>.json` exists (`report_digest`: origin, spread, top log findings, caveats; `--reports-dir`), and `build_code_context` sizes the source excerpts to what is left of `MAX_REQUEST_TOKENS` (estimated at `CHARS_PER_TOKEN`); `GroqProposer._ask` refuses a request estimated over `GROQ_TPM` before sending it. `MinuteBudget` makes consecutive calls in one process wait out the minute instead of being refused (separate CLI processes do not share it). `recommend.recommend_config` / `recommend_code` (used by the CLI and the graph) make one request and one proposal per fault (`agent.fault_groups`: faulted service + action; unnamed runs answer at most `MAX_FAULTS`), returning `Filed`. Agent 2's reports are read by `remediation/reports.py`; `policy.check_common` rejects evidence from an experiment whose report says its data is synthetic.
  - Code recommendations (`propose-code`) answer a declined config proposal with exact edits to the pinned upstream source (`source.py`: shallow clone at `docs/services.yaml` `source.commit` into git-ignored `.cache/upstream/`). Every service with source has a `services.yaml` `code:` map (`dir`; `serves`: RPC -> handler functions; `calls`: dependency -> call-site functions; frontend `pages`: probe -> handler). `agent.code_excerpts` shows the faulted services' `serves`, call sites on the failure path (direct calls into a faulted service, else one hop), and failed pages' handlers, within `MAX_CODE_LINES`. `source.find_function` resolves names per language (Go `func`; Python indentation, `Class.method` for duplicates; brace matching for C#/Java/Node). Each `CodeEdit` names a `function`; its `original` must match exactly once inside it, verbatim or line-by-line ignoring indentation (`source.find_matches`; exact only for Python, where indentation is syntax). `policy.check_code_proposal` limits files to the service's `code.dir`, edits and changed lines; `codelint.lint_edits` (pattern matching, no LLM) rejects an added or changed error branch that neither logs nor passes the error on, a comment claiming logging with no log call, a diagnosis of missing deadlines/timeouts with no edit adding one, and a Go `WithTimeout` whose cancel is never called; `code_excerpts` gives callers' call sites and failed pages the budget first for kill/stop/pause (the fix belongs in callers), the faulted service's own handlers only what is left; `source.build_check` runs in the first-stage image of the service's Dockerfile: gofmt + `go build` for Go, `dotnet build` for C#, `gradlew compileJava` for Java (package caches in volumes `remediation-gomod` / `-nuget` / `-gradle`; first C#/Java run takes minutes), `node --check` / `python -m py_compile` on the edited files for Node / Python (syntax only); a failed check is a policy rejection and `drop_format_only` keeps gofmt's fixes to untouched upstream lines out of the patch. The result is `patch.diff` (git-style, `git apply` at the upstream root), hashed into the approval like `override.yml`; `verify` refuses code proposals. `recommend.review_and_revise`: after the draft, the automated checks run, then a small reviewer call (`critique_code`: fault, diagnosis, patch, findings; `FAULT_MEANING` stops it demanding deadlines for kill/stop) can only list issues; any issue earns exactly one rewrite (`revision_note` as `build_code_context(extra=...)`), and the issues land on the review sheet (`CodeProposal.critique`, `revised`). `docs/services.yaml` `fix_recipes` (by fault, citing upstream code) go into the code context. Code effort is `CODE_REASONING_EFFORT` (medium: "high" failed 2/2 live), with a retry at the default on `CutOff` (token limit or Groq `json_validate_failed`). Groq counts the JSON schema at ~2.6x message text, so `wire_schema` sends it bare and puts the descriptions in the prompt as a field guide; `estimate_request` uses the two measured ratios. Measuring: each fault's calls share one Langfuse span (`tracing.span`), the proposal stores `trace_id`, filing scores `policy_clean` / `remediable` / `build` / `revised`, and `review` scores `human_decision`; `python -m remediation eval` replays all proposals against today's checks and saves a summary under `results/remediation/eval/`.
- `docs/services.yaml`: per-service facts read from the upstream v0.10.7 source (what each service reads, which calls are fatal to which page, deadlines). It is both agent context and the policy's env allow-list; cite source files when changing it.
- `agents/`: the LangGraph pipeline. START is always `attacker`, the last node before END is always `escalate` (writes `escalation`, the recommendation for human escalation; every early exit routes there too). `framework.add_agent` gives each agent three nodes: `<name>` (driver turn) -> conditional -> `<name>_tools` (a `ToolNode` over that agent's own tools, normal edge back) or `<name>_handoff` (turns the conversation into `PipelineState` fields, then the spec's conditional route). Each agent keeps its own message channel (`<name>_messages`); tools return `content_and_artifact`, and handoffs read the artifacts. Drivers: `llm_driver` (LangChain chat model with bound tools, `groq_chat_model`) or `scripted_driver` (fixed tool calls). The attacker is NOT built: real tools (`run_experiment` goes through the runner, so `validate_plan` still applies), scripted stand-in (runs the given plan). The reporter node (`agents/reporter.py`, there is no analyst) calls Agent 2 (`deps.reporter`, `Reporter.report_experiment_id`) once per experiment, saves the report to `reports/` (must differ from `results/`; tests set `reports_dir`) and forwards it as a finding; a failed report is a note, never a stop. Remediation reads those reports alongside `docs/services.yaml`. Remediation is scripted on purpose: its LLM calls happen inside its tools (`remediation/recommend.py`, shared with the CLI), config first, then code if declined and `allow_code`. `Deps` holds config, docker, a lazy proposer, a lazy reporter (`make_reporter`, `reports_dir`) and a runner factory; tests build on it.
- `agents/tracing.py`: Langfuse (v4, OTel-based). `run()` opens one root span per pipeline run with session/tags via `propagate_attributes` and supplies the LangChain `CallbackHandler` (nodes, tool calls and results). `generation()` records direct Groq SDK calls (`GroqProposer._ask`) with `usage_details` and `cost_details` from `PRICES` (USD per 1M tokens); it nests under the tool that made the call. `register_prices` creates Langfuse model definitions so handler-captured generations get a cost too. Everything is a no-op without `LANGFUSE_PUBLIC_KEY`/`LANGFUSE_SECRET_KEY`; `tests/conftest.py` clears them for every test.
- `agents/llm.py`: the reporter's (Agent 2) LLM seam. `get_client()` returns `RealClient` (Groq `openai/gpt-oss-20b`, `LLM_MODEL` overrides; strict JSON schema via `remediation.agent.wire_schema`, one retry on an invalid reply, traced as a generation) when `LLM_API_KEY` is set, else the rule-based `StubClient`; `Reporter._narrate` falls back to the stub on any `LLMError`, and `Report.narrator` records which one wrote it. `tests/conftest.py` sets `LLM_API_KEY=""` so tests never call the model.
- `planner/`: Agent 1, the experiment planner (the attacker), an LLM on a **constrained tool interface**. `catalogue.py` holds eight fault classes (`kill`, `stop`, `pause`, `throttle`, `memory_limit`, `network_partition`, `network_delay`, `flapping`; no `spike` - it is frontend-only), each runnable on any allowed service, with its param validation (reusing the injector's own functions) and the hypothesis / expected observations / recovery criteria a human reads. `plan.AttackPlan` is the structured plan (experiment id, cluster, target, action, params, hypothesis, expected observations, max duration, recovery criteria) and `to_experiment()` turns it into a `schemas.Experiment`. `policy.check_plan` is the independent pre-execution gate: it rejects unapproved attack types and unsafe params, then delegates target/duration/protected/health to `safety.validate_plan` (the same code the runner uses - nothing reaches Docker any other way). `interface.ToolInterface` exposes the eight typed `inject_*` tools plus read-only tools (`list_experiments`, `get_experiment_details`, `get_cluster_health`, `get_experiment_results`, `check_recovery`); every injection goes build -> policy -> approval -> runner -> audit. `approval.py` is human approval for every injection (CLI y/N, `pre_approved` ids for `--approve`, `AutoApprover` for an isolated env, `DenyAll` for dry runs/tests). `audit.Auditor` writes `results/plans/<session>/` (audit.jsonl of every tool request/policy decision/approval/result, each plan, the conclusion). `agent.py` selects experiments (Groq `PLANNER_MODEL` = `openai/gpt-oss-120b` via `agents.llm.get_client(model)` when `LLM_API_KEY` is set, else a deterministic blast-radius ranker registered as the `planner.select` stub handler, ranked from `docs/services.yaml` frontend `fatal` lists) and drives them through the tools. `ranking.py` (`planner rank`) ranks the five deadliest attacks against the current health (`get_cluster_health` now carries a per-service `services` snapshot: down, health-check ms, CPU, memory, restarts) without injecting anything; kill, pause and stop are excluded (`EXCLUDED`). The model's answer is cleaned like a plan (catalogue actions, allowed targets, params via the catalogue's validation, one per target) and topped up by the deterministic `score` (severity x blast radius x health modifiers), which is also the stub. It writes `results/attack_ranking.json`; the dashboard shows it beside the chaos tests and re-runs `planner rank` in a background subprocess every `BOUTIQUE_RANK_EVERY_S` (1800, 0 = button only; gpt-oss-120b on Groq's free tier is capped at 200k tokens a day). `console.py` is the dashboard's attack console: `planner interpret "REQUEST" --out F` reads plain words into one `AttackPlan` (120b, else the keyword `parse` stub) and policy-checks it without injecting; `planner execute F --confirm` re-checks and runs it via `ToolInterface.execute_plan` (shared with every `inject_*`) with `ConsoleApproval`, which approves only that experiment id. After a run, `planner execute` and `planner run` have Agent 2 report on each experiment from its `results/<id>.json` (as `orchestrator run` does; `--no-report` skips), then run the remediator the way the graph does (config recommendation, code recommendation for a declined one, all under one Langfuse span `remediation <ids>`; `--no-remediation`, `--no-build`), and the dashboard's Recent attack section follows the newest finished result, which exists only after rollback and recovery. So the dashboard can now start an experiment, but only one the operator saw and confirmed, through the policy and the runner; its kill switch lives in the sidebar. LLM-facing schemas use the typed `AttackParams`, never a free dict: Groq strict mode rejects objects without fixed properties. CLI: `python -m planner list | health | details <attack> | rank [--limit N] | interpret REQ [--out F] | execute F --confirm | run --goal ... --limit N [--approve ID ...] [--auto] [--dry-run]`.

Measured gotcha: on this Docker, the `kill` action counts as a manual stop, so `restart: unless-stopped` does not bring the container back; recovery comes from the rollback (`tests/fake_docker.py` still models self-healing on kill).

Invariants to keep: nothing under `safety/` calls an LLM; nothing reaches Docker without passing validation; `loadgenerator`, the dashboard and the monitor can never be targets.

## Tests

`tests/conftest.py` provides `results_dir` (tmp), `write_telemetry` / `make_sample` (samples in the monitor's real format, so tests exercise the production parsing path), `docker` (`FakeDocker`) and `config` (`TargetConfig`). New tests should build on these rather than mocking Docker or telemetry separately.
